You are looking at an implementation of the BEAT-MEV paper: “BEAT-MEV: Epochless Approach to Batched Threshold Encryption for MEV Prevention.”

High-level purpose:
This code implements a Batched Threshold Encryption (BTE) scheme for encrypted mempools. Users encrypt transactions under a committee public key. A block proposer selects a batch of ciphertexts. After finalization, committee members publish compact partial decryption shares for that batch. Anyone with at least t valid shares can combine them and decrypt exactly that batch. Ciphertexts outside the selected batch should remain private.

Core primitive:
The scheme combines:
1. A pairing-based key-homomorphic puncturable PRF.
2. Threshold ElGamal encryption “in the exponent.”
3. A Schnorr-style non-interactive zero-knowledge proof proving ciphertext well-formedness.
4. Optional sub-batching to trade more decryption-share communication for faster batch reconstruction and to avoid index coordination.

Main algorithms to look for:
- Setup(λ, Bmax):
  Creates public parameters for the puncturable PRF and pairing groups.
  This is a one-time setup tied to the PRF domain size / maximum batch size, not to committee secret shares.

- KeyGen(λ, n, t):
  Generates a threshold ElGamal keypair.
  The secret key is Shamir-shared among n committee members with threshold t.
  Each committee member gets one constant-size secret key share.
  The implementation may use a trusted dealer rather than a full DKG.

- Enc(pk, m, i):
  Encrypts message m at index i.
  Steps:
  1. Sample random PRF key k.
  2. Puncture k at index i, producing k*.
  3. Mask the message with the PRF value:
     gamma = m + PRF.Eval(k, i)
  4. Encrypt g^k using threshold ElGamal under the committee public key:
     ct = Enc(pk, g^k; u)
  5. Produce a NIZK proof π proving knowledge of k and ElGamal randomness u such that:
     - k* is a valid puncturing of k at index i.
     - ct is a valid ElGamal encryption of g^k using randomness u.
  6. Ciphertext shape should be conceptually:
     c = (i, k*, gamma, ct)
     with proof π.

- Verify(pk, c, π):
  Verifies the NIZK proof attached to a ciphertext.
  This is important for CCA security and rogue-ciphertext protection.
  Invalid ciphertexts should not be accepted into BatchDec.

- BatchDec(sk_l, {c_i}):
  Run by committee member l.
  It should:
  1. Verify every ciphertext proof in the batch.
  2. Multiply / aggregate all ElGamal ciphertext components in the batch.
  3. Produce one threshold ElGamal decryption share for the aggregated ciphertext.
  In the unoptimized scheme, each committee member publishes only one group element per batch.
  In sub-batching variants, each committee member publishes one share per sub-batch.

- Combine(pk, {d_l}, S, {c_i}):
  Public reconstruction/decryption after at least t valid shares are available.
  It should:
  1. Reconstruct the aggregate ElGamal plaintext K = g^(sum k_i) from threshold shares.
  2. For each ciphertext c_i, compute:
     m_i = gamma_i + sum_{j != i} PRF.PEval(k*_j, i) - PRF.ExpEval(K, i)
  3. Return all decrypted messages.
  This works because the PRF is key-homomorphic, so ExpEval on the aggregate key cancels the PRF masks.

Important correctness invariant:
All ciphertexts in the same sub-batch must have distinct puncture indices. If two ciphertexts in the same batch/sub-batch use the same index, decryption can fail.

Optimization / sub-batching:
The naive Combine cost is O(B^2) pairings because reconstructing every message involves evaluations against the other ciphertexts. The paper proposes splitting a large batch into α sub-batches. Each committee member publishes α decryption shares instead of one, but Combine becomes cheaper: roughly O(B * B/α) pairings. Common choices in the paper are α = sqrt(B) or α = 2*sqrt(B). This also helps remove the need for user coordination over unique indices.

Index coordination removal:
Instead of forcing every user to coordinate a unique index globally, each user samples an index randomly. The batch is sorted/grouped by repeated index count and then distributed across α sub-batches so identical indices land in different sub-batches. The system only needs to avoid too many collisions for the same index. This keeps ciphertext size constant, unlike approaches where users encrypt multiple times under multiple indices.

Security features to pay attention to:
- CCA security:
  The NIZK proof binds the ciphertext, public key, setup, punctured key, masked message, and ElGamal encryption. It should prevent “mauled ciphertext” and “copy attack” variants.

- Rogue ciphertext security:
  Malformed ciphertexts should not be able to poison batch decryption or leak information about pending transactions. This relies on Verify rejecting invalid proofs.

- Share verifiability:
  The paper discusses adding proofs to committee decryption shares so malformed shares can be identified and discarded. Check whether the implementation includes this or only benchmarks the base construction.

- Aggregation verifiability:
  The paper discusses verifiable aggregation so a third party can perform expensive Combine and prove correctness. Check whether this is implemented or only described as an optional extension.
